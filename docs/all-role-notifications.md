# การแจ้งเตือนทุกบทบาท

งานนี้อยู่ใน branch notifications ของ coe-next

## หน้าจอ

- /notifications: รายการส่วนตัวของผู้ใช้ที่เข้าสู่ระบบ ทั้ง 4 บทบาท
- กระดิ่ง: โหลดเมื่อเปิด ปิดเมื่อคลิกข้างนอกหรือเปลี่ยนหน้า
- อ่านทีละรายการ / อ่านทั้งหมด / เฉพาะยังไม่อ่าน / แบ่งหน้า 20 รายการ / รีเฟรช
- /api/student/notifications: เฉพาะนักศึกษา
- /api/member/notifications: เฉพาะเจ้าหน้าที่ กรรมการ แอดมิน
- /admin/notifications: รายการอีเมลล้มเหลว พร้อมเข้าคิวใหม่เมื่อครบจำนวนครั้งแล้ว
- ไม่เรียกฐานข้อมูลวนเบื้องหลัง ตัวเลขยังไม่อ่านครอบคลุมทุกรายการของบัญชี

## เหตุการณ์และผู้รับ

| ผู้รับ | เหตุการณ์ | ปลายทาง |
|---|---|---|
| เจ้าหน้าที่เจ้าของทุน | สมัครใหม่ / ส่งเอกสารแก้ไขกลับมา | /staff/review/:id |
| เจ้าหน้าที่เจ้าของทุน | ผลประเมินใหม่ / ผลครบ required_reviewer_count | /staff/review/:id |
| เจ้าหน้าที่เจ้าของทุน | ค้างจ่ายหลังอนุมัติและประกาศผลครบ 7 วัน | /staff/review/:id |
| กรรมการที่ได้รับมอบหมาย | งานใหม่ / เปลี่ยนงาน / ยกเลิกงาน | หน้าประเมินหรือ /committee |
| กรรมการที่ยังประเมินไม่เสร็จ | เปลี่ยนไฟล์เอกสารหลังมอบหมาย | /staff/evaluation?assignment=:id |
| กรรมการที่ยังประเมินไม่เสร็จ | ใกล้ครบกำหนดภายใน 48 ชั่วโมง | หน้าประเมิน |
| แอดมิน | pending_role ใหม่ (ถ้ามี) | /admin?status=pending |
| แอดมิน | เปลี่ยนบทบาทหรือเปิด/ระงับบัญชี | ค้นหาบัญชีใน /admin |
| แอดมิน | อีเมลล้มเหลวจนครบ max_retries | /admin/notifications |

ผู้รับผิดชอบทุนใน schema ปัจจุบันคือ scholarships.created_by (ผู้สร้างทุน)
ไม่ส่งข่าวใบสมัครให้เจ้าหน้าที่ทุกคนแล้ว ต้องรักษาบัญชีเจ้าของทุนให้ active
ระบบปัจจุบันให้แอดมินกำหนดบทบาทโดยตรง จึงไม่ได้เพิ่มหน้าขอบทบาทใหม่;
trigger รองรับ pending_role หากกระบวนการเดิมหรืออนาคตมีคำขอเข้ามา
การเปลี่ยนบัญชีเป็นการแจ้งเพื่อรับทราบและตรวจสอบ ไม่ได้หมายความว่าทุกครั้งเป็นข้อผิดพลาด

แจ้งเตือนค้างจ่ายครั้งเดียวต่อใบสมัคร/รอบอนุมัติ/รอบประกาศผล และเฉพาะยังไม่มี
disbursement สถานะ paid. นับ 7 วันจากวันล่าสุดระหว่างอนุมัติกับประกาศผล
กรรมการต้องมี due_at และใบสมัครยังอยู่ระหว่างประเมิน จึงได้รับเตือน 48 ชั่วโมง
แจ้งเตือนครบผลประเมินกันซ้ำต่อใบสมัคร/จำนวนกรรมการที่กำหนด
แจ้งอีเมลล้มเหลวให้แอดมินเฉพาะในเว็บ เพื่อไม่สร้างวงจรอีเมลล้มเหลวต่อเนื่อง
การเข้าคิวใหม่โดยแอดมินบันทึก audit และรอ dispatcher; ไม่ส่งทันที
การแจ้งผลประเมินให้เจ้าหน้าที่ไม่ใช่การประกาศผลให้ผู้สมัคร

## ติดตั้งฐานข้อมูล

ใช้ schema ล่าสุดของทีม รวม review_operations และ decouple_notification_outbox ก่อน:

1. ตั้งค่า .env.local ของ clone นี้จาก .env.example โดยไม่ commit secret
2. Supabase > SQL Editor > New query:
   รัน supabase/migrations/20260924010000_student_notification_read_all.sql
   ถ้ายังไม่เคยติดตั้ง (ไฟล์นี้รันซ้ำได้)
3. รัน supabase/migrations/20260924020000_all_role_notifications.sql ทั้งไฟล์หนึ่งครั้ง
4. เปิดเว็บด้วย npm run dev แล้วเข้าบัญชีแต่ละบทบาท

อย่า deploy โค้ด dispatcher ใหม่ก่อน migration เนื่องจากใช้ notification_email_batch RPC ใหม่
ยังไม่ได้รัน SQL หรือทดสอบอีเมลบน Supabase จริงในการพัฒนารอบนี้

## ตั้งเวลา

ใช้ scheduler ที่มีอยู่เรียก POST /api/notifications/dispatch ทุกชั่วโมง
ส่ง Authorization: Bearer <CRON_SECRET> หรือ <NOTIFICATION_DISPATCH_SECRET>
ตั้งค่าใน scheduler secret storage ห้ามใส่ใน URL หรือ commit ลง Git
endpoint นี้สร้าง reminders ก่อนส่งคิวอีเมล (ครั้งละไม่เกิน 20 รายการ)
ถ้าคิวมีปริมาณมากให้รอบส่งถี่ขึ้นตามขีดจำกัดผู้ให้บริการ
localhost ใช้จาก scheduler ภายนอกไม่ได้ ต้องใช้ URL ของเว็บที่ deploy แล้ว
การเพิ่ม migration ไม่ได้สร้าง scheduler ให้อัตโนมัติ
NOTIFICATION_APPS_SCRIPT_URL/SECRET และ SUPABASE_SECRET_KEY ต้องตั้งฝั่ง server
NEXT_PUBLIC_SITE_URL ต้องเป็น URL ที่ผู้รับอีเมลเปิดได้

## ตรวจสอบ

- node scripts/check-student-notifications.cjs: API ทั้ง 4 บทบาทและ template อีเมล
- node scripts/check-all-role-notifications-sql.cjs: PostgreSQL จำลองด้วย PGlite
  ติดตั้ง @electric-sql/pglite แยกในโฟลเดอร์ทดสอบ แล้วตั้ง PGLITE_MODULE ให้ชี้ package
  ทดสอบบน schema fixture ที่จำลองส่วนเกี่ยวข้อง ไม่ใช่สำเนา production ทั้งระบบ
- npm run build และ TypeScript/ESLint
- ทดสอบจริงด้วยบัญชีทดลอง: ส่งใบสมัคร > ขอแก้ไข > ส่งกลับ > มอบหมาย >
  ส่งผล > อ่านทั้งหมด > ตรวจว่าบัญชีอื่นไม่เปลี่ยนสถานะอ่าน
- ตรวจแจ้งเตือนค้างจ่าย / ใกล้ครบกำหนด และเรียก scheduler ซ้ำแล้วไม่มีแจ้งซ้ำ
- ตรวจอีเมลล้มเหลวครบครั้ง > แอดมินเห็น > เข้าคิวใหม่ > dispatcher ส่งใหม่
- การทดสอบ SQL จำลองไม่ยืนยันสิทธิ์/ข้อมูล/migration ของ Supabase ที่ใช้งานจริง
